# GlitchTip 이슈 처리

목표: 이슈마다 **확정 / 추정 / 미검증**이 구분된 판단과, 요청 범위에 맞는 조치를 남긴다.
가장 흔한 실패는 표면 신호로 단정하는 것이다: "HTTP 200이니까 성공", "에러 이름이 transport니까 네트워크 장애", "제목이 같으니 같은 원인", "최신 이벤트니까 그 사건". 아래 순서는 그걸 막기 위한 것이다.

- 프로젝트 고유 값(인스턴스, org, project ID, 코드 경로, 테스트 명령): `references/projects.md`. 이 GlitchTip 인스턴스(`glitchtip.thegame-sam.com`)의 이슈일 때만 적용한다. 다른 조직의 Sentry 사건에 이 값을 쓰지 않는다.
- Loki 교차 확인: `references/loki.md`.

## 0. 요청 범위 게이트

사용자가 무엇을 요청했는지로 종료 지점을 정한다.

| 요청 | 할 일 | 멈추는 곳 |
|---|---|---|
| "원인 봐줘", "조사해줘" | 1~5단계 | 보고(7단계) + 다음 선택지 제시. 코드 수정·PR 하지 않음 |
| "해결해줘", "고쳐줘" | 1~6단계 | 로컬 수정 + 테스트. PR은 요청이 있거나 이미 권한이 주어졌을 때만 |
| "PR 올려줘" | 6단계 PR 절차 | PR 생성 + CI 확인 |

GlitchTip 이슈 상태(resolve/ignore)는 요청이 있을 때만 바꾼다.

## 1. 입력 고정 (이슈별, 이벤트별로 따로)

각 이슈에 대해 아래를 표로 추린다. 시간·request_id가 다른 이벤트는 한 사건으로 섞지 않는다.

- 이슈 ID, **대상 이벤트 ID**, `dateCreated`(UTC), environment, project, release, count(발생 횟수)
- `tags`: `request_id`, `server_name`(pod), `release`, `environment`
- `contexts.trace.trace_id`
- `entries.exception.values[].stacktrace.frames` (앱 프레임만)
- `entries.breadcrumbs.values[]` (외부 호출 순서·상태)
- `user` (null이면 상관키로 못 쓴다)

### 조회 (GlitchTip MCP, `mcp__glitchtip__*`)

먼저 현재 세션에 GlitchTip MCP 도구가 활성화되어 있는지 확인한다. 주소·토큰 설정은 머신마다 다를 수 있다.

1. `get_issue({issue_id})` → 제목, count, firstSeen/lastSeen, project slug
2. 대상 이벤트 ID가 있으면 `get_event({event_id, organization_slug})`로 **그 이벤트**를 조회한다. 이 호출은 "You cannot call this from an async context" 오류로 실패한 적이 있다. 실패하면 호출·시각·메시지를 기록한다.
3. `get_latest_event({issue_id})`는 **대상 이벤트가 아닐 수 있다.** 받은 이벤트의 ID·timestamp를 대상과 대조하고, 다르면 "다른 표본"으로 표시하거나 사용자 제공 JSON/UI에서 정확한 이벤트를 확보한다.
4. `list_logs({organization_slug, project_id, environment, query: <request_id>, start, end})` → GlitchTip Logs. `[]`는 "GlitchTip Logs에 없음"일 뿐이다. Loki 조회가 아니다.

- 사용자가 이미 원본 JSON을 줬으면 다시 요청하지 않는다. MCP가 없고 JSON도 없으면 UI의 이벤트 JSON을 요청한다.
- count>1이면 대표 이벤트와 다른 발생들의 공통점/차이를 확인하거나 "표본 1건"이라고 표시한다.
- 앱의 `GLITCHTIP_DSN_*`는 **이벤트 전송용 DSN**이다. 조회 토큰으로 쓰지 않는다. 토큰·DSN 값은 어디에도 출력하지 않는다.

## 2. 이벤트 순서 재구성

breadcrumb로 외부 호출 순서를 시간순으로 다시 그린다 (예: S3 PUT → 외부 API POST → 상태 GET → 결과 GET → DELETE).

- 200/201은 **그 HTTP 요청이 성공했다**는 뜻일 뿐, 응답 본문(작업 완료, 결과 존재)의 성공을 증명하지 않는다.
- 빠진 호출이나 마지막 성공 호출은 **실패 구간을 좁히는 단서**다. 실패 지점 자체는 아니다. breadcrumb는 잘리거나 계측이 빠질 수 있고, 마지막 GET 이후 로컬 파싱이나 대기 중에 실패했을 수도 있다. 원래 예외, 사건 당시 코드, 로그로 확인한다.
- `content-length` 같은 크기 값으로 내용(무음 여부 등)을 추론하지 않는다.
- 저장 요청의 200(예: S3 PUT)은 DB가 그 파일을 참조하거나 사용자가 조회할 수 있다는 증거가 아니다. 최종 사용자 상태는 코드의 저장·DB 순서, 조회 API, 테스트로 확인한다.

## 3. 사건 당시 코드로 추적

현재 작업 트리가 아니라 **이벤트 release 커밋의 코드**를 읽는다.

```bash
git cat-file -t <release_sha>                       # commit인지 확인 (없으면 원격 브랜치 fetch)
git show --no-patch --format='%H %ci %s' <release_sha>
git show <release_sha>:<소스 경로>                   # 당시 catch/분기/저장 순서/로그 필드 확인
```

- 스택의 JS 경로·줄 번호는 빌드 산출물 기준이다. TS 소스와 줄 번호를 1:1로 맞추지 말고 **함수명·문장**으로 매핑한다.
- release 태그 형식(원시 SHA인지 가공된 값인지)을 가정하지 말고 이벤트의 실제 태그 값을 먼저 본다.
- 에러 코드/이름이 **포괄 `catch`에서 붙은 것인지** 확인한다. 포괄 catch 라벨(예: `dependency_transport`)은 실제 원인 종류를 말해주지 않는다.
- 같은 에러라도 **분기에 따라 부수효과(데이터 저장 여부)가 다를 수 있다.** 저장/전송 순서를 읽고 이슈별 "사용자 데이터 상태"를 적는다.
- 당시 코드의 **로그 필드 이름**(예: `requestId` vs `request_id`)을 확인해 둔다. Loki 검색에 필요하다.

## 4. 이슈 간 비교: 네 칸으로 분리

이슈별로 한 줄씩, 아래 칸을 섞지 않는다.

| 이슈 | 관측된 마지막 성공 | 앱이 던진 오류 | 입증된 원인 | 데이터 상태 |
|---|---|---|---|---|

- 앱 오류가 같아도 스택 경로와 데이터 상태가 다르면 UX나 수정이 따로 필요할 수 있다.
- 마지막 성공 호출이 다르다고 원인이 다르다고 단정하지 않고, 같다고 원인이 같다고 단정하지도 않는다. 같은 upstream 장애가 다르게 보일 수 있다.

## 5. 원인을 확정할 수 없을 때

결정적 증거(외부 응답 본문, 원래 예외, 입력 데이터)가 없으면 외부 제공자 내부 원인이나 사용자 입력 품질을 단정하지 않는다. 대신 세 층으로 나눠 적는다:

- **실패 트리거** (관측된 것): 예시 "전사 결과가 빈 문자열"
- **앱 결함** (지금 고칠 수 있는 것): 잘못된 에러 분류, 잘못된 재시도 UX, 데이터 유실, 포괄 catch로 인한 정보 손실
- **외부/근본 원인** (미검증으로 남기는 것): 예시 "제공자가 왜 빈 결과를 반환했는지"

다음 발생 때 진단할 수 있도록 **비민감 구조화 필드**를 로그와 GlitchTip 태그/컨텍스트에 추가하는 것을 수정 범위로 제안한다. 대상은 단계(stage), 사유(reason), HTTP 상태, 허용목록 기반 에러 타입, 재시도/폴링 횟수, 경과 ms, 저장 여부 같은 것이다. 원문 사용자 데이터(음성·텍스트), 외부 응답 본문, 외부 에러 메시지 원문, API 키는 남기지 않는다.

## 6. 수정과 PR (요청 범위 안에서)

- **깨끗한 base에서 시작**: 현재 트리에 무관한 미커밋 변경이 있으면 최신 base 브랜치(보통 `origin/dev`)에서 별도 worktree/브랜치를 만들고 관련 파일만 옮긴다. 옮긴 뒤에는 새 base에서 전체 테스트를 다시 돌린다. base에 새로 생긴 테스트와 충돌할 수 있다.
- 테스트는 이슈에서 확인한 분기별로 작성한다: 정상/실패 경로, 데이터 보존(최종 조회 상태까지), 상태 코드 구분, 로그에 민감정보가 없음. 프로젝트별 테스트 명령은 `references/projects.md`에 있다.
- 로컬 E2E를 돌릴 때는 서버가 **이 체크아웃의 코드**를 서비스하는지(빌드 SHA 등) 확인한다. 포트가 열려 있다는 사실만 믿지 않는다. 확인할 수 없으면 E2E 결과를 주장하지 않는다.
- PR 전: 최신 base를 fetch하고 전체 PR diff와 파일 목록을 확인한 뒤 `git diff --check`를 실행한다. 저장소에 PR 스킬(예: `create-pr`)이나 템플릿이 있으면 그 절차(Risk Level, Understanding Check 등)를 따른다.
- PR 본문에는 이슈별 **확인 근거 / 수정 / 한계** 표를 추가한다. 미검증 항목(배포 후 재발, 외부 원인)은 한계에 적는다.
- PR 후: base/head, 파일 수, 본문을 확인하고 CI가 끝날 때까지 결과를 확인한다.
- `.env`, 토큰, DSN 값은 커밋·PR에 넣지 않는다.

## 7. 보고 형식

```markdown
## GlitchTip #<id> — <한 줄 요약>
| 이슈 | 관측된 마지막 성공 | 앱이 던진 오류 | 입증된 원인 | 데이터 상태 |
|---|---|---|---|---|

### 증거 경계
- 확정: <원본 이벤트/당시 코드/테스트로 재확인한 사실>
- 추정: <순서·분기에서 도출했지만 원문으로 확인 못 한 것>
- 미검증: <근본 원인, 배포 후 재발 여부 등>

### 원인 층
- 실패 트리거 / 앱 결함 / 외부 원인(미검증)

### 조치 (또는 조사만 요청된 경우: 다음 선택지)
- 수정: <PR 링크, 범위>
- 진단 추가: <추가한 필드>
- 검증: <실행한 테스트와 결과 / 실행 못 한 것>

### 조회 기록
- <MCP 호출, LogQL, 시간 범위, 결과 요약, 도구 실패와 대체 경로>
```

조회(MCP 호출, LogQL, 시간 범위)와 결과 요약은 **실행 즉시** 기록한다. 그러지 않으면 나중에 "실제로 실행한 쿼리"와 "예시"를 구분할 수 없게 된다.
